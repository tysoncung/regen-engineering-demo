title: Concurrent duplicate registrations yield exactly one success
status: active
since: 2026-07-31
affects: [customer]
implemented_by: [customer]

---

Two simultaneous registrations of the same email produce exactly one 201 and
one 409, never two accounts.

Recorded after a Regeneration Test reported guessing at it. Both current
implementations satisfy it by construction (a single-threaded event loop in one
case, a lock across check-and-insert in the other), but "by construction" is
exactly the kind of knowledge that silently fails to survive regeneration into
a runtime with different concurrency defaults.

Verified by CT-005, which fires ten registrations together rather than in
sequence. A sequential loop would pass against an implementation with no
atomicity at all, which is the failure this requirement exists to catch.
