> **Draft, reconciled from a hotfix. Not agreed knowledge.** This rule describes
> what the running code does after commit `30d52e6`. It has not been reviewed
> against what the system *should* do, and it contradicts two rules that are
> already active. Read [ISS-002](../issues/ISS-002.md) before treating any of
> this as settled.

`GET /customers/{id}/addresses` returns at most **fifty** addresses.

When a customer holds more than fifty, the response contains the fifty most
recently **added** addresses and omits the older ones. "Recent" here means order
of creation, not the order-of-use recency that [BR-002](BR-002.md) uses for
default promotion; the two senses of the word now both appear in this module.
The fifty that are returned remain in oldest-first order among themselves, so
the ordering the caller sees is unchanged, only its beginning is missing.

The response carries no indication that anything was omitted. It is the same
bare JSON array, with no total, no cursor, no `next` link and no header. A
caller receiving fifty addresses cannot distinguish a customer who holds exactly
fifty from one who holds four thousand, and has no way to ask for the rest. The
omitted addresses remain addressable individually by id through `PATCH` and
`DELETE`, so they are hidden from the list and from nothing else.

The cap applies to every customer, including deleted ones, and it is applied
after the 404 for an unknown customer.

## Fifty is arbitrary

Fifty was chosen during an incident and is not derived from anything. The
commit that introduced it gives one reason, that a page was timing out, and no
measurement: no page-weight budget, no response-time target, no observed
address count, and no evidence that the address list was the cause rather than a
correlate. Nothing establishes that fifty is correct, only that it is what
stopped the bleeding. See [ASM-002](../assumptions/ASM-002.md) for the beliefs
this rule is resting on, none of which are verified.

Unlike [BR-011](BR-011.md), which states plainly that twenty is a product limit
chosen to keep the address book navigable, fifty has no stated purpose. If this
rule is accepted, the number needs one; if it cannot be given one, that is an
argument for rejecting the rule rather than for writing the number down more
neatly.

## Not verified by a contract

There is no contract for this rule, and one cannot currently be written.
[BR-011](BR-011.md) caps a customer's address book at twenty, so a contract
cannot construct a customer holding fifty-one addresses through the documented
interface, and therefore cannot observe the truncation at all. The behaviour is
unreachable through the API it belongs to. That is the contradiction, stated as
a testing problem: see [ISS-002](../issues/ISS-002.md).

Leaving a rule unverified is normally knowledge debt to be paid down. Here the
missing contract is not debt but evidence, and writing a contract that skipped
the public API to reach the state would launder the incoherence rather than
expose it.
